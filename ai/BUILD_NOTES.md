## Service worker and caching

- `sw.js` is **cache-first**: it serves `index.html` / `app.js` / `style.css` straight from cache and never diffs against the network. Any change to those three is invisible to the installed PWA until `CACHE_NAME` is bumped. The symptom is "I changed it and nothing happened" — it is not a code bug. Bumping the string forces install → activate → old cache deleted → fresh fetch. Last observed version: **`vantageprm-cache-v95`** (Session 2A.5's third bump; confirmed still v95 on disk and in `caches.keys()` at the 2A.6 phase close).
- **A late fix needs its own bump, and the review pass is a bump trigger like any other.** Once a version has installed and activated, any further edit to `app.js` / `index.html` / `style.css` is invisible under that same `CACHE_NAME` — bumping once at the start of a session does not cover an edit made after the first verification pass. **Phase 1 measured this: across eleven sessions, v65 → v83 is 19 bumps, and not one session finished on a single bump.** The trigger is usually not a code defect the session could have caught — it is a decision only real use produces (1.6's reachout reversal, 1.10's bulk-bar move, 1.8's resize-zone geometry). **Budget two bumps per session and do not record a one-bump win before Michael's review pass.**

- **A cache-first service worker means the FIRST reload after a bump still serves the OLD document.** The new `sw.js` is fetched, installs, `skipWaiting()`s and claims — but all of that finishes after the current page has already been served from the old cache. **The second reload gets the new build.** This surfaced 2026-08-30 as a bug report against Session 1.10 ("the bulk bar didn't move") when the file on disk was already correct. **Give every shipped change a one-glance version tell** and hand it over with the summary — for 1.10 it was "is '+ New Task' still in the TaskHub header?", because the button's removal and the layout change rode the same bump.
- **`install` does `cache.addAll(ASSETS)`, and `ASSETS` includes a Google Fonts URL — `addAll` is all-or-nothing.** If that one cross-origin request fails (offline, DNS, a blocked network), **install rejects, the new worker never activates at all, and the old cache keeps serving indefinitely.** The symptom is identical to the one above except no number of reloads fixes it. If a bump appears to do nothing after two reloads, check DevTools → Application → Service Workers for a worker stuck in "installing"/"redundant" before suspecting the code.

## Working inside app.js

- One file, ~13,270 lines. **Always search for the exact function before editing it** — do not navigate by scrolling or by assumed location. This is a workaround for a structural issue, not a style preference.
- `index.html` is ~174 KB of markup in one document. Modal and section ids must stay globally unique.

- `check_ids.py` in the repo root cross-checks `getElementById()` calls inside `setupEventListeners()` against ids actually present in `index.html`. Crude, but it catches the listener-bound-to-a-nonexistent-element class of failure in one command.
- **`app.js` declares `let state` at line 5, so `state` is NOT `window.state`.** A top-level `let` in a classic script binds in the global *lexical* environment, which is not a property of `window`. A bare `state` in the console or inside a Playwright `page.evaluate()` works; `window.state` is `undefined`, and a `waitForFunction` written against it hangs until it times out with nothing to show for it. This cost one wasted 15-second harness run in Session 1.6. **Automated checks must reference `state` bare, guarded by a `try/catch` for the pre-boot window** — the same applies to every other top-level `let` in the file, which is most of them (`taskSelectedIds`, `aqSelectedIds`, `editingTaskId`, …).
- **`check_ids.py` has a standing baseline of two, and it is not a failure.** It reports `{'export-backup-btn', 'restore-backup-input'}` on a clean tree. Both are read behind explicit `if (el)` guards under the comment "Safely guarded for older elements" — deliberately optional markup, not a bug. **Read the output as a diff against that pair**, not as "must be empty," and run it on the unmodified tree first if there is any doubt. ## DOM and rendering

- **`innerHTML +=` destroys existing event listeners.** Use `createElement` + `appendChild` whenever the element being added carries a listener. This has bitten the audience inspector specifically.
- Inspector panels use two intentionally different patterns. Prospect Hub uses `.prospect-inspector-panel` — an absolutely-positioned overlay that animates in with `translateX`. The Campaign Hub Audience view puts `#audience-inspector` in as a direct grid child.
- Because of that, the Audience view's container carries an inline `grid-template-columns: 1.2fr 0.9fr; gap: 16px` override in `index.html`. `.prospects-layout-container` defaults to `1fr 0fr`, which collapses the inspector to zero width — the DOM updates correctly and nothing appears to happen. **Do not remove that inline style or "fix" it to match the Prospect Hub pattern.**
- Render functions that read DOM elements should early-return when one is missing — `renderAudienceInspector()` does. A missing element otherwise throws a `TypeError` that kills the entire render, not just that panel.
- **The prospect inspector's "Add to audience…" control lives OUTSIDE the three memberships subsections, at the top of `#inspector-memberships`, on purpose.** It is the one path in that panel that mutates another entity, and keeping it out of the subsection structure means a future restructure of Campaigns/Audiences/Tasks cannot reach it. Do not tidy it into the Audiences subsection.
- **Navigating from the inspector to a Campaign Hub record takes three steps, not one.** `switchView("campaigns")` alone lands on whatever sub-tab was last open. An audience needs `campaignViewSubState = "audiences"` + `selectedAudienceListId = id` + `renderCampaignsView()`; a campaign needs `campaignViewSubState = "campaigns"` + `renderCampaignsView()` + `openCampaignDetail(id)`. `campaignViewSubState` and `selectedAudienceListId` are module-scope variables, not state fields, so they do not survive a reload — that is fine for navigation and wrong for anything persisted.
- **`var(--color-danger)` is defined NOWHERE in `style.css`, and it has SIX live call sites, not one.** An undefined custom property makes the declaration invalid at computed-value time, so the element silently inherits. Recounted 2026-08-30 at the Phase 1 close: `app.js` 7775 / 8065 / 8498 (three delete buttons — email-accounts row, domains row, audience trigger) and `index.html` 1680 / 2582 / 2704 (Clear Selection plus two Delete buttons), **plus** `app.js` 8024, `renderDomainsView()`'s expired-domain highlight, which is the one the earlier note named. So five destructive controls across three hubs render in inherited text colour instead of red, and the expired-domain signal is dead. The three `style.css` hits are comments warning about exactly this. Do not reach for that token in new code — the file's convention is literal hex (`#ef4444`, `#10b981`), and TaskHub's row states define real classes with `.light-theme` overrides. Found 2026-08-29 (Session 1.5), scope corrected 2026-08-30; carried to Phase 2 backlog. **Defining the token once is a smaller fix than the earlier note implied and it repairs all six.**
- **Two adjacent surfaces that LOOK like one bar must share a ground token, not two tokens that happen to be close (Session 2A.5 review).** `#canvas-header` sat on a translucent `rgba(244,245,247,.25)` over `#main-canvas`'s `--color-base` `#f4f5f7`. That composites to `#f4f5f7` **exactly** — blending a colour with itself changes nothing, so the alpha bought no translucency at all — while `#sidebar` sat on `--color-sidebar-bg` `#eaecef`. **A 10/9/8 RGB step straight down the seam, in light theme only:** the same two tokens in dark are `#09090b` and `#0c0c0e`, a step of 3, which is invisible. That asymmetry is why it survived a twelve-screenshot sweep across both themes and was caught by eye afterwards — **when a defect can only exist in one theme, the theme that hides it will out-vote the one that shows it in any per-hub screenshot pass.** Fixed by giving `#canvas-header` the same `--color-sidebar-bg` ground, which also let the `.light-theme` override and an inert `backdrop-filter` go (an opaque background makes a backdrop blur do nothing, and `#canvas-body` is the header's flex SIBLING — nothing ever passes beneath it). **Second, smaller cause worth knowing separately:** the sidebar's tint ramps vertically over the full column while the header's ramps horizontally, so along the seam the header holds `--hub-tint-strong` for the strip's whole height but a two-stop vertical ramp had already decayed to 27.5% by the bottom of it — a 1/5/2 wedge on top of the base step. The sidebar gradient is now three stops, holding the strong stop to `var(--app-strip-height)` before it fades, so the two are identical down the entire seam and the decay belongs to the column below the band. **The general rule: to prove two surfaces match, composite them arithmetically and diff the channels.** Reading two `background-color` strings and judging them similar is how a 10-unit step ships.
- **A flex `gap` is charged between items even when an item is `width: 0`, and in the 76px collapsed rail that silently CROPS the logo (Session 2A.5).** `#sidebar-brand` carries `gap: 12px` and, when collapsed, holds a `--brand-logo-size` logo plus `#brand-name` at `width: 0; opacity: 0`. The flex line therefore measures logo + 12 + 0, not logo. At 40px that fitted; the moment the logo passed 64px the line exceeded the rail, and **centring an OVERFLOWING line puts its start at a negative offset**, where `#sidebar`'s `overflow: hidden` crops the left edge. Measured at 68px before the fix: `logo.left: -2`, `logo.right: 66` against a sidebar `0 → 76` — 2px shaved off one side, 10px of dead space on the other. Fixed with `gap: 0` in the collapsed brand rule, which is what `.nav-tab` and `.sidebar-action-btn` already do there; the brand box was the one collapsed row that had never needed it. **The rail is why `--brand-logo-size` cannot exceed 72px** — past that it crops rather than shrinks. **The general lesson is the diagnostic, not the rule:** a cropped element reports its full declared width from `getBoundingClientRect()`, so `width: 68` looks correct while 2px of it are not on screen. **Compare the element's `left`/`right` against its clipping ancestor's**; the width alone proves nothing.

Verified 2026-08-30 restoring a 651-prospect backup that predated TaskHub: the 31 existing tasks survived. Useful, and a trap — see the orphan note below.

- **`convertToCSV()` quotes every field unconditionally and `parseCSV()` tracks quote state across newlines, so multi-paragraph values round-trip exactly** — verified in Session 1.3 against a note holding blank lines, commas and embedded `"` quotes, character-identical after export → wipe → restore. Both halves are required (this is Phase 1 C6, and it is the general pattern for any new enum value).
- **A scalar setting rides in `prm_settings.csv` as a `["Name", value]` row** behind a `sawX` guard, following `Custom Sort Order`. That one row is what gives a settings object its DIRECTIVES §4 backup coverage — cheaper than a file of its own, and it restores through every path the settings CSV already reaches.
- New fields need a default in the existing state-defaults path (`ensureStateDefaults()` / `initializeDefaultState()`), or records predating the field read `undefined` and downstream code breaks on restore rather than on save — so the failure surfaces long after the change.
- `ensureStateDefaults()` always runs after a restore. That is the hook restore relies on for migrations.
- A feature that only mutates already-covered fields needs no new backup work. Check before assuming — the Advanced Query feature needed none. Session 1.6 was a second instance: it mutates `state.tasks[].status`/`.completedDate` and `p.history` only, both already exported and restored, so it added zero export or restore code.
- **`hist-${Date.now()}` collides inside any loop, and duplicate history ids are destructive, not cosmetic.** `recordInteraction()` mints one id per user action, so the idiom is safe there and unsafe the moment anything writes several entries in one pass — a bulk action completes three tasks in the same millisecond and gets three identical ids. `deleteInteraction()` filters on `h.id !== histId`, so deleting one entry would silently delete every twin, and the user sees two extra rows vanish with no error. - **A reachout is contact with a human — email, DM, phone call — and nothing else belongs in the reachout math.** Scope §8 originally counted task completion as a reachout; Michael reversed it on 2026-08-29 (scope §14), hours after Session 1.6 shipped it. - **The single-writer rule survives its first "interesting" case, and that is the test it had to pass.** §14.4's transposition — a completion that really *was* contact logging an `Email` rather than a `"Task Completed"` — is one `reachoutType` parameter threaded `saveTaskFromEditor()` → `completeTask()` → `logTaskCompletionHistory()`, defaulting to `null`. Any future history variant follows the same shape: a parameter on the existing writer, never a sibling function.
- **A JSON payload survives the settings CSV intact — verified for real, not by inference.** Session 1.10's C17 row is `["Column Layouts", JSON.stringify(state.columnLayouts)]`, whose value is full of `"` characters; `convertToCSV()` writes it as `"{""taskhub"":{""order"":[""dueDate"",…]}}"` and `parseCSV()` reads it back. - **`state.columnLayouts` is the app's one persisted-UI-layout record, and future layout state joins it rather than starting a sibling.** Keyed by table id (`taskhub` is the only key in Phase 1), so a second table adopts it without a second implementation. - **The read-side migration rule is what makes a layout record safe, and it belongs in ONE resolver.** `taskHubColumns()` drops keys the build does not know and appends known columns the saved order never mentioned; `taskHubColumnWidth()` treats `0`/absent as "use the code default". - **Exactly one function may write a given history entry type, and every path must route through it.** Scope §8's failure mode is the reason: a completion path that skips history does not throw, does not warn, and does not look wrong — `getLastReachoutDate()` simply under-reports, and the Advanced Query date filters keep returning results that are quietly incorrect. ## Dates

- Store `YYYY-MM-DD` strings, not ISO timestamps. Timestamps inherit the off-by-one-day timezone bug class that already bit the Onyva weather date filter. Date-only strings compare cleanly as text, including for before/after/on filters.
- **`new Date().toISOString().split("T")[0]` is the file's oldest date idiom and it is UTC, not local.** It appears ~20 times in `app.js`. In America/New_York it produces *tomorrow's* date for anything created after 8pm — exactly the off-by-one class above, hiding inside the convention that was supposed to prevent it. **Task dates use `todayLocalDateStr()` instead** (defined next to `getCompanyName()`, Session 1.4). Use it for any new date field; leave the existing call sites alone unless a session is already touching them, since changing them is a data-meaning change, not a refactor.

- **Day-stepping arithmetic must run in UTC, not local time.** `shiftTaskDate()` (Session 1.7, contract C11) advances a `Date` one day at a time. A local-time `d.setDate(d.getDate() + 1)` across a spring-forward boundary lands on the *same* calendar day it started, because that local day is 23 hours — so a "+5 business days" shift silently arrives four days out, twice a year, in a way no test run in July will ever show. `Date.UTC(y, m, d)` days are always 24 hours. **Parse `YYYY-MM-DD` into UTC fields, step with `setUTCDate()`, read back with `getUTCFullYear/Month/Date`, and never let a local offset touch the value.** This is the same off-by-one-day class as the `toISOString()` note above, arriving from the other direction: there the bug is *reading* a local moment as UTC, here it is *doing arithmetic* in local time.

## Driving this app from an automated browser

- **A native dialog blocks every subsequent CDP/extension command — the tab goes unresponsive and only a human can clear it.** `wipeAllData()`, `resetSandbox()` and `makeNewSandbox()` all gate on `prompt()`; `wipeAllData()` also ends in `alert()`, and the restore path alerts twice (`applyJSONBackupText`, then the attachment count). The session looks hung, not failed — it cost ~15 minutes in Session 1.8 before the cause was identified. **Stub `window.prompt` / `window.alert` / `window.confirm` into a capture array before calling anything that raises one, and restore them in a `finally`.** The real function body still runs unmodified, which is the point — it tests the shipped code, not a reimplementation. Do not "fix" this by removing the alerts; they are the right behavior for a human.
- **`exportZIPBackup()` ends in `saveBackupFile(name, blob)` and returns before the blob exists** (`zip.generateAsync(...).then(...)`). To capture the export for an automated round trip, wrap `saveBackupFile` to stash `(name, content)` and call through to the original, then poll for the stash — awaiting `exportZIPBackup()` alone is not enough. Calling through matters: it still writes the real file to the backup folder, which is the rollback point.
- **A CDP-synthesized `left_click_drag` does not drive these drag handlers.** They bind `mousemove`/`mouseup` on `document`, and the synthesized drag produced a mousedown that entered the resize branch but no width change. Dispatching real `MouseEvent`s (`mousedown` on the element from `elementFromPoint`, then a series of `mousemove` on `document`, then `mouseup`) works and is the same pattern BUILD_NOTES already recommends for clicks.

- **A synthesized drag does not fire the trailing `click` — so it cannot test C16 row 3 on its own.** A real browser dispatches `click` after `mouseup` on the same element, and that click is what consumes `layoutSuppressNextHeaderClick`. Dispatching only `mousedown`/`mousemove`/`mouseup` leaves the flag standing, and the next thing you check reads `true` and looks like a leak when nothing has leaked. **To verify "the click after a drag does nothing and the one after that behaves normally," dispatch the `click` yourself immediately after the `mouseup`**, then two ordinary clicks (each `mousedown` → `mouseup` → `click`), and read `taskSort` after each. Verified this way in Session 2B.2: sort unchanged after the drag's own click, `asc` after the next, `desc` after the one following.
- **The screenshot a browser tool returns is LETTERBOXED when Chrome's page zoom is not 100%, and the blank band at the bottom is not the app failing to fill the window.** Michael's Chrome runs at 75% zoom (`devicePixelRatio` reports `0.75`), and the captures come back 1157×1062 with the real viewport occupying only the top ~793 rows. It reads exactly like "the layout stops three-quarters of the way down," which is the single most alarming thing a layout session can see, and it is an artifact of the capture. **Settle it in one call instead of debugging the CSS:** append two `position: fixed` probe bars — one at `bottom: 0`, one at `top: 50%` — screenshot, and check that the bottom bar sits at the true viewport edge and the middle bar at half of it. Session 2A.1 lost several minutes to this before probing. `document.documentElement.scrollHeight === innerHeight` is the cheap companion check that the page is not scrolling.
- **`Page.captureScreenshot` times out after 30s roughly half the time on this app, and the very next identical call succeeds. This is NORMAL, and the cause is known: the automation tab is backgrounded.** Observed three times in Session 2A.1, on about half of a twelve-screenshot sweep in 2A.5, and again through the 2A.6 close sweep — every retry succeeded, on pages that were demonstrably responsive (JS evaluated normally either side of each failure). **Retry once and move on. Do not go looking for a blocking dialog** unless a second attempt also fails — a real native dialog is the other cause, and it does not clear on retry. *(Merged at the 2A.6 curation from two entries that said this separately.)*
- **To force a scroll in a view whose entity list is empty, inject rows into the `<tbody>` (or card grid) directly and never touch `state`.** Michael's live database has 0 campaigns, 0 email accounts and 0 domains, so three of CampaignHub's five sub-views cannot be made to scroll with real data at all. Tag the injected nodes (`data-synthetic="1"`), remove them when done, and reload before the final verification pass — the reload is what proves nothing leaked into storage. **Never reach for `saveState()` or a real create path to manufacture screenshot data** in a hub whose records are Michael's actual outreach.
- **"Did I cause this, or was it already there?" is answered by injecting an `!important` override stylesheet at runtime, not by reverting the file.** Append a `<style>` that force-disables exactly the rules the session added, measure, remove it, measure again, and print both. It takes one call, needs no rebuild, no cache bump and no reload, and it produces a number pair rather than a recollection. - **`scrollHeight` never reports less than `clientHeight`, so `scrollHeight === height` is NOT evidence that a region is full or that it can scroll.** A card 832px tall holding 771px of content reports `scrollHeight: 829` — its own client height — and reads exactly like "content fills the box." The check that means something is **`el.scrollHeight > el.clientHeight`**, and the way to prove a converted region actually scrolls is to inject enough tagged filler to make that true and watch `#canvas-body` stay put. Session 2A.3 lost one measurement round to reading the raw number instead.
- **If the Chrome window gets MINIMIZED mid-session, `resize_window` cannot recover it and every screenshot is garbage until it is.** Observed 2026-08-31 (Session 2A.5): captures came back 614×262 showing the `max-width: 900px` mobile layout — hamburger, no sidebar — which reads exactly like a responsive bug in the CSS you just wrote. **The tell is `screenX`/`screenY` reporting `-32000`** (Windows' minimized sentinel), with `outerWidth: 160, outerHeight: 28`. `resize_window` fails with "Bounds must be at least 50% within visible screen space" because it sets size but not position, and cannot move the window back on screen. **The fix that worked: close the tab so the group auto-removes, then `tabs_context_mcp{createIfEmpty: true}`, which opens a FRESH window at a normal position.** Do not spend attempts on `resize_window`; two failures is enough. - **The extension's content filter blocks on OBJECT KEY NAMES and on query strings, not just on the `window.prompt` reassignment already noted above.** Session 2A.5 got `[BLOCKED: Sensitive key]` for an otherwise inert result object because one of its keys was named `tokens` (it held CSS custom-property values), and `[BLOCKED: Cookie/query string data]` for a string that was simply the first line of `sw.js`, fetched with a `?bust=` cache-buster. The surrounding keys came back fine, so **the block is per-value, and renaming the key (`tokens` → `vars`) returns the same data**. It is the tool refusing to send, not the page failing — there is nothing to debug in the app.
- **NEVER wrap a `javascript_tool` script in an async IIFE — it returns `{}`.** The tool has REPL semantics and returns the last expression, and an `async () => {…}()` evaluates to a Promise it does not await, which serialises as an empty object. It looks exactly like "the page returned nothing". **Use top-level `await` with a bare final expression instead** (`const x = await fetch(...); ({x})`). Cost two dead calls in Session 2A.5.
- **To prove a navigation replay actually restores a sub-state, POISON the sub-state first — otherwise the test passes on code that never restored anything (Session 2B.1).** CampaignHub is reached through three module-scope cursors plus a render, and `campaignViewSubState` / `selectedAudienceListId` usually already hold the values a replay is supposed to put back, so "click back, read them, they're right" is satisfied by a bare `switchView("campaigns")`. Set them to something else *while the other view is open* (`campaignViewSubState = "domains"; selectedAudienceListId = null`), then replay, then read — and read the sub-views' `className` too, not just the variables, since the variable can be right while `renderCampaignsView()` was never called. The same shape applies to any "returns you to where you were" check in this app: **arrange for the correct answer to be wrong before you ask.**
- **Hidden file inputs can be driven.** `#data-restore-input` carries `class="hidden"`; removing that class and moving the node to `<body>` makes it hittable, and moving a node preserves its listeners. Give it an `aria-label` so an accessibility-tree `find` can locate it.

- **The Chrome extension's content filter can REFUSE a `javascript_tool` script that reassigns `window.prompt` / `window.alert` / `window.confirm`.** Session 2A.4 got `[BLOCKED: Cookie/query string data]` on two different phrasings of the dialog stub this file recommends above — an array-and-loop version and a plain three-assignment version — while ordinary scripts either side of them ran fine. The block is the tool refusing to send, not the page failing, so there is nothing to debug in the app. **Do not spend attempts rewording it.** The fallback that worked: read the render path first and confirm it raises no dialog — `renderDataManagementView()` and its two callees `renderSnapshotStatusPanel()` and `updateBackupFolderUI()` contain no `alert`/`confirm`/`prompt` call at all — then enter the hub and **click nothing**. The stub is only genuinely required for a session that intends to invoke `wipeAllData()`, `resetSandbox()`, `makeNewSandbox()` or a restore; merely rendering DataHub does not need it.
- **A BACKGROUNDED automation tab gets no animation frames, so in-flight CSS transitions FREEZE at their start value and `getComputedStyle` reports the frozen number as though it were settled.** This produced a full false alarm on 2026-08-31: `#sidebar` reported `width: 76px` (collapsed) while `classList` said `sidebar-pinned`, `matches('#sidebar:not(.sidebar-pinned):not(:hover)')` returned **false**, there was no inline width, and injecting `width: 280px !important` changed nothing. Every state check said "should be 280" and the computed value said 76. **The tell is `el.getAnimations()` returning entries with `playState: "running"` and `currentTime: 0` that never advance**, plus `document.visibilityState === "hidden"`. The app was never wrong. **Before measuring layout in an automated tab, inject `*, *::before, *::after { transition: none !important; animation: none !important; }`** — with it in place the same element measured 280px and `getAnimations()` dropped to 0. Leave it in for the screenshot pass too; it only removes settling animations. This is the third form of "a passing state check is not evidence" in this file, inverted: here the state checks were right and the *computed value* was the liar. **It bites HARDEST on the first measurement after a reload, and it is not limited to width.** Session 2A.5's review pass measured `#sidebar` and `#canvas-header` as `rgb(12,12,14)` — the DARK ground — while `document.body.className` read `light-theme module-dashboard` and `state.theme` read `"light"`. The cause: the document parses with no theme class, `initTheme()` adds `.light-theme` during boot, the `background-color` transition starts, and a hidden tab never advances it, so computed style reports the dark START value indefinitely. `document.getAnimations().length` was **108**; injecting the kill-switch dropped it to 0 and both elements immediately read `rgb(234,236,239)`. **Inject the stylesheet after EVERY reload, not once per session** — the reload discards it along with the rest of the document. **Re-inject after a theme toggle too**, which starts a fresh set of `background-color` transitions. With the kill-switch in place `document.getAnimations().length` reads **0**, and that number is the cheap proof the measurement you are about to take is real; the 2A.6 close read 0 before every measurement and every value settled first try.

  **Two corollaries that used to be filed as their own notes and are the same fact:** (1) **`getBoundingClientRect().width` read straight after toggling a class that animates width returns the OLD value while `getComputedStyle().width` returns the new one** — the sidebar's 0.3s collapse still reported 280px from the rect 500ms later while computed style already said 76px. Rect reads the animated value; computed reads the resolved target. (2) So the instrument depends on the question: **for "did the class take effect," read computed style; for "what does the user see right now," take the screenshot** — and with the kill-switch injected the two agree, which is the whole reason to inject it. *(Merged at the 2A.6 curation.)*
- **NEVER `await` a `requestAnimationFrame` in a `javascript_tool` call.** A hidden tab never fires rAF, so the promise never settles and the whole CDP `Runtime.evaluate` hangs until it times out at 45 seconds with nothing to show. Use `setTimeout` for every wait in an automated script. Cost one dead 45-second call on 2026-08-31 — and the timeout was itself the clue that the tab was not being rendered.

## Traps carried into Phase 4 (hosting)

*Renamed 2026-08-30: hosting moved from Phase 2 to Phase 4 in `DECISIONS.md` on 2026-08-28, and three standing files kept the stale number. Full pre-flight, with the items that cannot be deferred, is `ai/spec/phase-4-firebase-preflight.md`.*

Full reasoning in `DECISIONS.md`; these are here because this file is read every session and that one is not.

- **The blob shortcut.** Storing whole state as one hosted document caps at the 1 MB document limit and lets two devices overwrite each other wholesale — a silent total overwrite, not a merge conflict. Rejected on Gate B. If a future session proposes it as a quick win, read `DECISIONS.md` before agreeing.
- **The origin trap.** Today's data lives on the `localhost:5000` origin. A hosted app is a different origin with a different `localStorage` and **opens empty**. Prospects do not follow. The ZIP/CSV backup is the bridge, and Phase 4 needs an explicit import-and-verify step. Doing real work in a hosted copy before that produces two divergent databases.
- **The `saveState()` risk.** Granular writes sound like touching every mutation site across 10,000 lines. They are not: keep a shadow copy of last-saved state, diff on save, write only what changed. One function, no call sites touched. This converts the riskiest session in the build into an ordinary one.
- **The Gmail scope cliff.** `gmail.send` is a sensitive scope and cheap. *Reading* mail is restricted and buys a recurring annual third-party security assessment. "Detect the reply and auto-advance the sequence" sounds small and is not.

## Local snapshot backup (Phase 1 deliverable)

- File System Access API: `showDirectoryPicker()` once, persist the handle, write without re-prompting. Chrome and Edge only — not Safari, not Firefox. Vantage runs in Chrome app mode, so this is fine today and is a real constraint if the app is ever opened elsewhere. The permission occasionally needs re-granting, which is why a denied or failed write must surface visibly rather than log and continue.

### Health, honesty and the failure modes

- **A `beforeunload` snapshot leaves a real, correctly-named, ZERO-BYTE file when the page dies mid-write.** `createWritable()` creates the file immediately; if the page tears down before `write`/`close`, the file persists at 0 bytes and the read-back check never runs to catch it. The next boot then listed it as the newest snapshot, stamped `lastConfirmedAt` from its mtime, and showed **green while the newest snapshot on disk was empty** — precisely the lie C13 exists to prevent. **Fix: `listSnapshotFiles()` skips zero-byte files**, applying the writer's non-zero-size standard on the read side too. Do not remove that check. `beforeunload` additionally now only writes when there is an unprotected mutation, so reloads stop manufacturing corpses.
- **Anything called from `evaluateSnapshotHealth()` runs on every single `saveState()`.** The Data Management status panel listed the snapshots directory (a `getFile()` per entry) and it was landing behind every mutation in the app. It is now gated on `state.activeView === "data-management"`. The sidebar chip is the always-on surface and must stay cheap — it reads only the in-memory health object.
- **The permission model is per browser profile, not per app.** The File System Access directory handle lives in IndexedDB on the origin *in that profile*. A second Chrome profile (or the installed PWA if it runs under a different profile) opens with **no** backup folder and goes red. A session that verifies snapshots in one profile has proven nothing about another.
- **`showDirectoryPicker()` cannot be driven by an agent** — it opens a native OS dialog. Any session whose Done-when touches the backup folder needs Michael to click once. Clicking the health chip is the shortest path: with no folder set it opens the picker, and with one set it forces a snapshot.
- **Console read-back caveat for agent-driven verification:** Claude in Chrome's `read_console_messages` returns the whole tab history and stamps every message with the *read* time, not the emit time. Ordering within a read is therefore not evidence of ordering in the app. Clear the buffer, reload, then read, or you will chase phantom failures that are just replayed history.

### Retention, the mirror, and running a drill

- **An agent can run the full export → wipe → restore drill without a file dialog** by temporarily replacing `window.saveBackupFile` with a capture function, calling the real `exportZIPBackup()`, and feeding the captured blob back through the real `processRestoreFile()` as a `new File([blob], name)`. Only the final write-to-disk step is stubbed; the ZIP assembly, the router and every restore function are the real ones. This is how Session 1.3's Done-when was run.
- **Snapshot time comes from the FILENAME, never from mtime.** Every file in a backup folder restored from cloud sync, copied to a new machine, or seeded by a test arrives with mtime set to the copy time. Reading mtime then reports a ten-week-old snapshot as written just now — precisely the C13 lie. `parseSnapshotName()` is the authority and `listSnapshotFiles()` carries the parsed value as `at`. This is also why a seeding drill's health-chip readings are meaningless: the chip is honest about *when the snapshot was taken*, and seeded files claim old dates.
- **Retention day/week buckets are the most recent buckets that CONTAIN snapshots, not calendar windows.** Read as "the last 14 calendar days," two weeks away from the app leaves rules 2 and 3 matching nothing, and the first run back prunes to the rolling 10 — deleting history exactly when it is least replaceable.
- **`planSnapshotRetention(files)` is deliberately pure** — an array in, a Map of name → surviving rules out, no directory handle anywhere. That is what makes ten years of fabricated dates testable in node in a second. The 30-file drill was *predicted* from it and then matched against the real pruner; keep that separation if the rules are ever amended.
- **Zero-byte corpses are now self-cleaning.** A reload can still leave one (see the 1.1 finding above); expect at most one boot warning, after which the pruner sweeps it. A *recurring* warning across many boots now means the pruner is not running, which is a real signal rather than known noise.
- **The mirror never deletes**, even when the attachment is deleted in the app — an older snapshot may still reference the blob. It also never re-writes an id it already holds, so a forced re-run is free and the mtimes on `snapshots/files/` do not move. Both are load-bearing: a mirror that forgets in step with the live database is not a recovery mirror.
- **Two browser profiles pointed at ONE backup folder is a trap, and it fires twice.** The handle is per profile (1.1 finding above), but the *folder* can be the same one — and then: (1) health lies. `initSnapshotSystem()` stamps `lastConfirmedAt` from the newest file in the directory with no notion of which database wrote it, so a profile whose own writer is dead boots **green** off another profile's snapshots. (2) Retention cannibalizes. A busy profile's snapshots fill the rolling-10 and the day buckets, pruning the quieter profile's history away. Neither the watchdog nor the pruner can tell two databases apart, because nothing in a snapshot identifies its origin. **Give each profile its own backup folder** unless and until snapshots carry a database id. Identified 2026-08-29 while handing off 1.2 — the sandbox profile was green and correct, and would have gone on looking correct after production was pointed at the same folder.
- The pruner touches `snapshots/files/` three guards deep — entry kind, name pattern, and an explicit name check. Any refactor of the directory walk must keep all three; deleting that directory silently strips every attachment from every snapshot that references one.
