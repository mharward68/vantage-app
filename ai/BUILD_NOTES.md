- **THE COLUMN-RESIZE CURSOR IS ONE CSS CUSTOM PROPERTY AND `app.js` HOLDS ONLY A REFERENCE TO IT (Session 2B.12).** `--cursor-col-resize` is declared in `style.css` `:root`, immediately after `--color-danger`: a 24x24 inline-SVG data URI, black glyph, white halo, hotspot `12 12`, with `, col-resize` as a mandatory keyword fallback. `app.js`'s `LAYOUT_RESIZE_CURSOR` (beside `LAYOUT_MIN_COL_PX`) is the string `"var(--cursor-col-resize)"` — **not a second copy of the 692-character URI**, because the CSS copy is not optional and two copies is how the hover cursor and the drag cursor eventually stop matching. Verified before being relied on: `el.style.cursor = "var(--cursor-col-resize)"` set from JS does resolve to the full `url(...)` at computed-value time.

  **WHY A BITMAP AT ALL, so nobody "simplifies" it back to the keyword.** The stock `col-resize` cursor is drawn by Windows with a mask and takes its colour from whatever is beneath it. On the light-purple ProspectHub header it resolved to nearly the header's own luminance and all but vanished; dark mode was always fine. This is **not** a stacking-context or occlusion problem — the OS composites the pointer above everything the page paints — and chasing `z-index` here is a dead end the review pass already walked.

  **⚠️ THE MID-DRAG FIX IS TWO INDEPENDENT CHANGES IN THE SAME HANDLER AND EITHER ONE ALONE IS A FALSE PASS.** (1) `layoutResizeLive`, a module-scope boolean set in `initHeaderDrag()`'s resize branch and cleared in its `onUp`, makes the thead `mousemove` return early so it stops wiping the inline cursor off the th being dragged. (2) `document.body.classList.add("layout-resizing")` **REPLACED** the old `document.body.style.cursor = "col-resize"`, and pairs with `body.layout-resizing, body.layout-resizing * { cursor: var(--cursor-col-resize) !important; }` in the `TASKHUB LAYOUT` block. **An inherited body cursor loses to ANY descendant that sets its own** — `.taskhub-sortable` sets `cursor: pointer` on every TaskHub header — so the body inline could never have worked, and the guard alone only protects the th the drag STARTED on, not the neighbour the pointer crosses two frames later. The `*` and the `!important` are the point of the rule, not enthusiasm.

## Service worker and caching

- `sw.js` is **cache-first**: it serves `index.html` / `app.js` / `style.css` straight from cache and never diffs against the network. Any change to those three is invisible to the installed PWA until `CACHE_NAME` is bumped. The symptom is "I changed it and nothing happened" — it is not a code bug. Bumping the string forces install → activate → old cache deleted → fresh fetch. Last observed version: **`vantageprm-cache-v126`** (Session 2B.15, 2026-09-03 — one bump, confirmed live with `controlled: true` and a new-global probe). **v96 → v126 is 30 bumps across Phase 2B's 21 sessions — 1.4 per session, the first phase to come in UNDER the two-per-session budget.** ⚠️ **This number goes stale the moment anyone ships; treat it as "roughly where the counter is", never as a version check** — see the two `toString()` traps and the `caches.keys()` warning below.
- **A late fix needs its own bump, and the review pass is a bump trigger like any other.** Once a version has installed and activated, any further edit to `app.js` / `index.html` / `style.css` is invisible under that same `CACHE_NAME` — bumping once at the start of a session does not cover an edit made after the first verification pass. **Phase 1 measured this: across eleven sessions, v65 → v83 is 19 bumps, and not one session finished on a single bump.** Session 2B.3 needed its second bump for a CSS fix found *by measuring during the verification pass* — not by review, and not a code defect — which is one more shape the trigger takes. The trigger is usually not a code defect the session could have caught — it is a decision only real use produces (1.6's reachout reversal, 1.10's bulk-bar move, 1.8's resize-zone geometry). **Budget two bumps per session and do not record a one-bump win before Michael's review pass.**

- **A cache-first service worker means the FIRST reload after a bump still serves the OLD document.** The new `sw.js` is fetched, installs, `skipWaiting()`s and claims — but all of that finishes after the current page has already been served from the old cache. **The second reload gets the new build.** This surfaced 2026-08-30 as a bug report against Session 1.10 ("the bulk bar didn't move") when the file on disk was already correct. **Give every shipped change a one-glance version tell** and hand it over with the summary — for 1.10 it was "is '+ New Task' still in the TaskHub header?", because the button's removal and the layout change rode the same bump.
- **`install` does `cache.addAll(ASSETS)`, and `ASSETS` includes a Google Fonts URL — `addAll` is all-or-nothing.** If that one cross-origin request fails (offline, DNS, a blocked network), **install rejects, the new worker never activates at all, and the old cache keeps serving indefinitely.** The symptom is identical to the one above except no number of reloads fixes it. If a bump appears to do nothing after two reloads, check DevTools → Application → Service Workers for a worker stuck in "installing"/"redundant" before suspecting the code.

- **A THIRD WAY A BUMP APPEARS NOT TO LAND, AND ITS SYMPTOM IS INVERTED FROM THE OTHER TWO: a stale ACTIVATED registration on an UNCONTROLLED page.** Found 2026-09-01 at the 2B.4 handover, on Michael's real Chrome. `caches.keys()` returned **only `vantageprm-cache-v98`** while `sw.js` on disk plainly read `const CACHE_NAME = 'vantageprm-cache-v100'` — **and the page was nevertheless running the brand-new `app.js`.** That combination is the tell, and it is the opposite of the two failures above: there the code was stale and the cache explained why; here the **code was fresh and only the cache name looked wrong.** The reason is `navigator.serviceWorker.controller === null` — nothing was intercepting fetches, so `npx serve` handed the browser the real files off disk, while an old **already-activated** v98 worker sat in the registration and the v100 worker never reached `installing` at all. **Reloading does not fix it; neither does restarting the server or opening a fresh window** (all three were tried). **The diagnostic is one paste, and it distinguishes all three failure modes at once:**
  ```js
  const rs = await navigator.serviceWorker.getRegistrations(); const t = await (await fetch("./sw.js",{cache:"no-store"})).text(); JSON.stringify({caches: await caches.keys(), swFileFirstLine: t.split("\n")[0], controlled: !!navigator.serviceWorker.controller, regs: rs.map(r=>({installing:r.installing&&r.installing.state, waiting:r.waiting&&r.waiting.state, active:r.active&&r.active.state}))})
  ```
  Read it as: something in `installing`/`redundant` → the Google-Fonts `addAll` failure above. `waiting` populated → an ordinary pending update, one more reload. **`controlled: false` with `active: "activated"` and the file already showing the new version → this case.** **The fix is to unregister and drop the caches, then reload:**
  ```js
  const rs = await navigator.serviceWorker.getRegistrations(); await Promise.all(rs.map(r => r.unregister())); await Promise.all((await caches.keys()).map(k => caches.delete(k)));
  ```
  **This is data-safe — unregistering a worker and deleting its caches touches neither `localStorage` nor IndexedDB**, so the database and the attachment store are untouched; say so when asking Michael to run it, because it reads like a destructive command and is not. Confirmed resolved the same morning: `['vantageprm-cache-v100']`, `controlled: true`. **The wider lesson is that `caches.keys()` alone is NOT a version check** — it answers "what has this worker cached", not "what code is this page running". Pair it with something the new build actually renders (2B.4 used the tab strip's six labels) or the two can disagree in either direction.
- **What a genuinely clean boot console looks like on this app, so a future session stops re-deriving it:** five lines — `[Database] Loaded from localStorage` (or `Seeded successfully from prm_data.json` on a first run), `[IndexedDB] VantagePRMFiles database connected.`, `[PWA] Service Worker registered`, and one or more `[Snapshot]` lines (`Boot: newest on disk is …`, `Pruned N file(s) … kept`, `Mirror (daily): …`). **One red line is expected and is NOT app code: `Failed to load resource: 404 (Not Found)` for `/favicon.ico`** — the browser asking for a tab icon the server does not serve. It is intermittent, depending on whether the service worker answers the request. Cosmetic; a `<link rel="icon">` in `index.html` fixes it and it is on the Phase 2B backlog. **Anything else in red is real.**

- **⚠️⚠️ A VERSION PROBE READ OFF `Function.prototype.toString()` LIES IN BOTH DIRECTIONS, AND IT LIED IN BOTH DIRECTIONS IN A SINGLE CALL (Session 2B.14).** Confirming "is the page running my new code" by searching a live function's source is the right instinct — `caches.keys()` alone is not a version check, as the note above says — but the obvious markers are the ones that fail.
  - **FALSE POSITIVE: the identifier you added already exists in the OLD code, in a branch you did not touch.** 2B.14 changed the *include* half of `matchesIncludeExclude()` from `hasAll` to `hasAny`, and probed for `hasAny`. It came back true **on the v124 build** — because the untouched *exclude* half has said `const hasAny = …` since long before. Same trap in `matchesIncludeExcludeSmart()` with `matchesAll`/`matchesAny`. Two of three probes reported "new code" on a page that was entirely old, and the third (`matchesTagsFilter`) correctly reported old — **the mixed result is what exposed it, and a mixed result from one file is impossible, so treat any disagreement between probes as a broken probe rather than a partial deploy.**
  - **FALSE NEGATIVE: `toString()` INCLUDES COMMENTS INSIDE THE FUNCTION BODY.** The same session probed `renderProspectsView.toString().includes("companyTagQueries")` to prove a deleted identifier was gone. It came back present — from the *comment* the session had just written explaining the deletion.
  - **THE RULE: probe for a token that exists in exactly one of the two versions and appears in no comment.** The one that worked was `includeSet).some(` versus `includeSet).every(` — punctuation-anchored, unwriteable in prose, and checked in BOTH directions in the same expression so "neither matched" is distinguishable from "the new one matched". **Better still, probe by BEHAVIOUR:** call the function with an input whose answer differs between versions (`matchesTagsFilter(["a"], "a,zzz")` — true on the new build, false on the old). A behavioural probe cannot be fooled by a comment or a same-named variable.
  - **And the ordinary cache-first trap is what put an old build in front of these probes in the first place:** first reload after a bump serves the old document while `caches.keys()` already reports the NEW name and `controlled` is already true. That combination — new cache name, old code — is normal on reload #1, and is not the stale-registration case described above.

## Dates

- Store `YYYY-MM-DD` strings, not ISO timestamps. Timestamps inherit the off-by-one-day timezone bug class that already bit the Onyva weather date filter. Date-only strings compare cleanly as text, including for before/after/on filters.
- **`new Date().toISOString().split("T")[0]` is the file's oldest date idiom and it is UTC, not local.** It appears ~20 times in `app.js`. In America/New_York it produces *tomorrow's* date for anything created after 8pm — exactly the off-by-one class above, hiding inside the convention that was supposed to prevent it. **Task dates use `todayLocalDateStr()` instead** (defined next to `getCompanyName()`, Session 1.4). Use it for any new date field; leave the existing call sites alone unless a session is already touching them, since changing them is a data-meaning change, not a refactor.

- **Day-stepping arithmetic must run in UTC, not local time.** `shiftTaskDate()` (Session 1.7, contract C11) advances a `Date` one day at a time. A local-time `d.setDate(d.getDate() + 1)` across a spring-forward boundary lands on the *same* calendar day it started, because that local day is 23 hours — so a "+5 business days" shift silently arrives four days out, twice a year, in a way no test run in July will ever show. `Date.UTC(y, m, d)` days are always 24 hours. **Parse `YYYY-MM-DD` into UTC fields, step with `setUTCDate()`, read back with `getUTCFullYear/Month/Date`, and never let a local offset touch the value.** This is the same off-by-one-day class as the `toISOString()` note above, arriving from the other direction: there the bug is *reading* a local moment as UTC, here it is *doing arithmetic* in local time.

## Traps carried into Phase 4 (hosting)

- **The blob shortcut.** Storing whole state as one hosted document caps at the 1 MB document limit and lets two devices overwrite each other wholesale — a silent total overwrite, not a merge conflict. - **The origin trap.** Today's data lives on the `localhost:5000` origin. A hosted app is a different origin with a different `localStorage` and **opens empty**. Prospects do not follow. ## Local snapshot backup (Phase 1 deliverable)

- File System Access API: `showDirectoryPicker()` once, persist the handle, write without re-prompting. Chrome and Edge only — not Safari, not Firefox. Vantage runs in Chrome app mode, so this is fine today and is a real constraint if the app is ever opened elsewhere. ### Health, honesty and the failure modes

- **A `beforeunload` snapshot leaves a real, correctly-named, ZERO-BYTE file when the page dies mid-write.** `createWritable()` creates the file immediately; if the page tears down before `write`/`close`, the file persists at 0 bytes and the read-back check never runs to catch it. The next boot then listed it as the newest snapshot, stamped `lastConfirmedAt` from its mtime, and showed **green while the newest snapshot on disk was empty** — precisely the lie C13 exists to prevent. **Fix: `listSnapshotFiles()` skips zero-byte files**, applying the writer's non-zero-size standard on the read side too. Do not remove that check. `beforeunload` additionally now only writes when there is an unprotected mutation, so reloads stop manufacturing corpses.

  **SETTLED 2026-09-01 (Session 2B.8): THE PRUNER DELETES THE FILE IT SAYS IT DELETES.** Session 2B.6 logged `Ignoring 1 zero-byte snapshot file(s)` together with `Pruned 1 file(s) — 1 zero-byte, 0 aged out. 13 kept.` and flagged two readings — an occasional truncated write, or a pruner reporting a deletion it never performs. 2B.7 booted clean and could not choose. 2B.8 caught the pair on one boot (10:11:32) and **the very next boot nine seconds later logged NEITHER line**. The pruner is honest and the read-side skip is doing its job; what remains is only that a truncated write happens occasionally, which is the race this section already describes. **Not an open question any more — do not re-open it on the next sighting.**
- **Anything called from `evaluateSnapshotHealth()` runs on every single `saveState()`.** The Data Management status panel listed the snapshots directory (a `getFile()` per entry) and it was landing behind every mutation in the app. It is now gated on `state.activeView === "data-management"`. The sidebar chip is the always-on surface and must stay cheap — it reads only the in-memory health object.
- **The permission model is per browser profile, not per app.** The File System Access directory handle lives in IndexedDB on the origin *in that profile*. A second Chrome profile (or the installed PWA if it runs under a different profile) opens with **no** backup folder and goes red. A session that verifies snapshots in one profile has proven nothing about another.
- **`showDirectoryPicker()` cannot be driven by an agent** — it opens a native OS dialog. Any session whose Done-when touches the backup folder needs Michael to click once. Clicking the health chip is the shortest path: with no folder set it opens the picker, and with one set it forces a snapshot.
- **Console read-back caveat for agent-driven verification:** Claude in Chrome's `read_console_messages` returns the whole tab history and stamps every message with the *read* time, not the emit time. Ordering within a read is therefore not evidence of ordering in the app. Clear the buffer, reload, then read, or you will chase phantom failures that are just replayed history.

### Retention, the mirror, and running a drill

- **An agent can run the full export → wipe → restore drill without a file dialog** by temporarily replacing `window.saveBackupFile` with a capture function, calling the real `exportZIPBackup()`, and feeding the captured blob back through the real `processRestoreFile()` as a `new File([blob], name)`. Only the final write-to-disk step is stubbed; the ZIP assembly, the router and every restore function are the real ones. This is how Session 1.3's Done-when was run.
- **Snapshot time comes from the FILENAME, never from mtime.** Every file in a backup folder restored from cloud sync, copied to a new machine, or seeded by a test arrives with mtime set to the copy time. Reading mtime then reports a ten-week-old snapshot as written just now — precisely the C13 lie. `parseSnapshotName()` is the authority and `listSnapshotFiles()` carries the parsed value as `at`. This is also why a seeding drill's health-chip readings are meaningless: the chip is honest about *when the snapshot was taken*, and seeded files claim old dates.
- **Retention day/week buckets are the most recent buckets that CONTAIN snapshots, not calendar windows.** Read as "the last 14 calendar days," two weeks away from the app leaves rules 2 and 3 matching nothing, and the first run back prunes to the rolling 10 — deleting history exactly when it is least replaceable.
- **`planSnapshotRetention(files)` is deliberately pure** — an array in, a Map of name → surviving rules out, no directory handle anywhere. That is what makes ten years of fabricated dates testable in node in a second. The 30-file drill was *predicted* from it and then matched against the real pruner; keep that separation if the rules are ever amended.
- **Zero-byte corpses are now self-cleaning.** A reload can still leave one (see the 1.1 finding above); expect at most one boot warning, after which the pruner sweeps it. A *recurring* warning across many boots now means the pruner is not running, which is a real signal rather than known noise.
- **The mirror never deletes**, even when the attachment is deleted in the app — an older snapshot may still reference the blob. It also never re-writes an id it already holds, so a forced re-run is free and the mtimes on `snapshots/files/` do not move. Both are load-bearing: a mirror that forgets in step with the live database is not a recovery mirror.
- **Two browser profiles pointed at ONE backup folder is a trap, and it fires twice.** The handle is per profile (1.1 finding above), but the *folder* can be the same one — and then: (1) health lies. `initSnapshotSystem()` stamps `lastConfirmedAt` from the newest file in the directory with no notion of which database wrote it, so a profile whose own writer is dead boots **green** off another profile's snapshots. (2) Retention cannibalizes. A busy profile's snapshots fill the rolling-10 and the day buckets, pruning the quieter profile's history away. Neither the watchdog nor the pruner can tell two databases apart, because nothing in a snapshot identifies its origin. **Give each profile its own backup folder** unless and until snapshots carry a database id. Identified 2026-08-29 while handing off 1.2 — the sandbox profile was green and correct, and would have gone on looking correct after production was pointed at the same folder.
- The pruner touches `snapshots/files/` three guards deep — entry kind, name pattern, and an explicit name check. Any refactor of the directory walk must keep all three; deleting that directory silently strips every attachment from every snapshot that references one.
