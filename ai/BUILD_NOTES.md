## Service worker and caching

- `sw.js` is **cache-first**: it serves `index.html` / `app.js` / `style.css` straight from cache and never diffs against the network. Any change to those three is invisible to the installed PWA until `CACHE_NAME` is bumped. The symptom is "I changed it and nothing happened" — it is not a code bug. Bumping the string forces install → activate → old cache deleted → fresh fetch. Last observed version: `vantageprm-cache-v80`.
- **A late fix needs its own bump.** Once a version has installed and activated in the browser, any further edit to `app.js` / `index.html` / `style.css` is invisible under that same `CACHE_NAME` — bumping once at the start of a session does not cover an edit made after the first verification pass. Session 1.3 shipped v65, made a one-line fix, and needed v66. Session 1.4 needed three — v67, then v68 and v69 for two in-session corrections after verification had already run. Session 1.5 needed three — v70 to ship, then v71 and v72 for fixes found during Michael's review pass afterwards. Session 1.6 shipped v73, then v74 the same day for the scope §14 reachout amendment — a decision made in review, which is the same trigger. Session 1.9 shipped v76, then v77 the same day for a stacking defect Michael found in review — so the count still stands at zero sessions finishing in one bump. **The review pass is a bump trigger like any other**; a session is not finished bumping until the person looking at it stops finding things. Session 1.10 shipped **v78**, then **v79** the same day for a §15.1 amendment Michael asked for after using it. **The count still stands at zero sessions finishing in one bump**, and 1.10 is the sharpest case yet: its two *code* defects were caught in-session by its own screenshots, and the bump it still needed was for a decision only real use could produce. Session 1.11 shipped **v80** and ended its own run on one bump — **the count is only settled after Michael's review pass, so budget for a second bump rather than recording a win early.**

- **A cache-first service worker means the FIRST reload after a bump still serves the OLD document.** The new `sw.js` is fetched, installs, `skipWaiting()`s and claims — but all of that finishes after the current page has already been served from the old cache. **The second reload gets the new build.** This surfaced 2026-08-30 as a bug report against Session 1.10 ("the bulk bar didn't move") when the file on disk was already correct. **Give every shipped change a one-glance version tell** and hand it over with the summary — for 1.10 it was "is '+ New Task' still in the TaskHub header?", because the button's removal and the layout change rode the same bump.
- **`install` does `cache.addAll(ASSETS)`, and `ASSETS` includes a Google Fonts URL — `addAll` is all-or-nothing.** If that one cross-origin request fails (offline, DNS, a blocked network), **install rejects, the new worker never activates at all, and the old cache keeps serving indefinitely.** The symptom is identical to the one above except no number of reloads fixes it. If a bump appears to do nothing after two reloads, check DevTools → Application → Service Workers for a worker stuck in "installing"/"redundant" before suspecting the code.

## Working inside app.js

- One file, ~10,000 lines. **Always search for the exact function before editing it** — do not navigate by scrolling or by assumed location. This is a workaround for a structural issue, not a style preference.
- `index.html` is ~157 KB of markup in one document. Modal and section ids must stay globally unique.
- A single feature routinely spans the prospect modal, the inspector, CSV export, CSV restore, `ensureStateDefaults()` and two or more views — scattered, never adjacent. Budget for the spread when sizing a session.
- `check_ids.py` in the repo root cross-checks `getElementById()` calls inside `setupEventListeners()` against ids actually present in `index.html`. Crude, but it catches the listener-bound-to-a-nonexistent-element class of failure in one command.
- **`app.js` declares `let state` at line 5, so `state` is NOT `window.state`.** A top-level `let` in a classic script binds in the global *lexical* environment, which is not a property of `window`. A bare `state` in the console or inside a Playwright `page.evaluate()` works; `window.state` is `undefined`, and a `waitForFunction` written against it hangs until it times out with nothing to show for it. This cost one wasted 15-second harness run in Session 1.6. **Automated checks must reference `state` bare, guarded by a `try/catch` for the pre-boot window** — the same applies to every other top-level `let` in the file, which is most of them (`taskSelectedIds`, `aqSelectedIds`, `editingTaskId`, …).
- **`check_ids.py` has a standing baseline of two, and it is not a failure.** It reports `{'export-backup-btn', 'restore-backup-input'}` on a clean tree. Both are read behind explicit `if (el)` guards under the comment "Safely guarded for older elements" — deliberately optional markup, not a bug. **Read the output as a diff against that pair**, not as "must be empty," and run it on the unmodified tree first if there is any doubt. Confirmed identical before and after Sessions 1.4 and 1.5.

## DOM and rendering

- **`innerHTML +=` destroys existing event listeners.** Use `createElement` + `appendChild` whenever the element being added carries a listener. This has bitten the audience inspector specifically.
- Inspector panels use two intentionally different patterns. Prospect Hub uses `.prospect-inspector-panel` — an absolutely-positioned overlay that animates in with `translateX`. The Campaign Hub Audience view puts `#audience-inspector` in as a direct grid child.
- Because of that, the Audience view's container carries an inline `grid-template-columns: 1.2fr 0.9fr; gap: 16px` override in `index.html`. `.prospects-layout-container` defaults to `1fr 0fr`, which collapses the inspector to zero width — the DOM updates correctly and nothing appears to happen. **Do not remove that inline style or "fix" it to match the Prospect Hub pattern.**
- Render functions that read DOM elements should early-return when one is missing — `renderAudienceInspector()` does. A missing element otherwise throws a `TypeError` that kills the entire render, not just that panel.
- **The prospect inspector's "Add to audience…" control lives OUTSIDE the three memberships subsections, at the top of `#inspector-memberships`, on purpose.** It is the one path in that panel that mutates another entity, and keeping it out of the subsection structure means a future restructure of Campaigns/Audiences/Tasks cannot reach it. Do not tidy it into the Audiences subsection.
- **Navigating from the inspector to a Campaign Hub record takes three steps, not one.** `switchView("campaigns")` alone lands on whatever sub-tab was last open. An audience needs `campaignViewSubState = "audiences"` + `selectedAudienceListId = id` + `renderCampaignsView()`; a campaign needs `campaignViewSubState = "campaigns"` + `renderCampaignsView()` + `openCampaignDetail(id)`. `campaignViewSubState` and `selectedAudienceListId` are module-scope variables, not state fields, so they do not survive a reload — that is fine for navigation and wrong for anything persisted.
- **`var(--color-danger)` is used in `app.js` but defined NOWHERE in `style.css`.** `renderDomainsView()` reads it for the expired-domain highlight; an undefined custom property makes the declaration invalid at computed-value time, so the cell simply inherits and the "expired" signal is silently dead. Do not reach for that token in new code — the file's actual convention is literal hex (`#ef4444`, `#10b981`), and TaskHub's row states define real classes with `.light-theme` overrides instead. Found 2026-08-29 (Session 1.5); the domain fix is backlogged, out of compartment.
- **Native date inputs need their calendar glyph tinted, or it is invisible in dark mode.** Chrome's `::-webkit-calendar-picker-indicator` ships a near-black icon; on this app's `#09090b` canvas it cannot be seen, so `<input type="date">` looks like a plain text field and the picker looks missing. It cost a scope request for a feature that already existed. Fixed 2026-08-29 in the `📅 NATIVE DATE INPUT` block of `style.css`: `background: var(--color-primary)` shown through a `mask` carrying the glyph as an SVG data URI in `--calendar-glyph`. **Mask, not `filter`** — a filter chain that lands on a specific hue is six magic numbers that cannot be rethemed, and the token approach follows the hub color for free. Note `getComputedStyle` cannot read author styles on that pseudo-element, so **verify it visually; a computed-style probe reports the rule as absent even when it is applied.**
- **Every `.modal-overlay` is `z-index: 200`, so when one modal opens another, DOM ORDER decides which one the user can actually touch.** The loser opens correctly, sets its fields correctly, reports every class and value correctly — and is unreachable behind the winner. `#modal-prospect` / `#modal-company` / `#modal-choose-tags` were lifted to `z-index: 999999` for this reason; `#modal-task` joined them 2026-08-30 after the orphan resolution window (`#modal-task-orphans`, later in `index.html`) painted over the editor it had just opened. **Any new modal that can be opened from another modal belongs in that list** — check DOM order rather than assuming, because at equal z-index it is a coin flip decided by markup position.
- **A stacking bug is invisible to state-based verification, and that is the whole lesson.** Session 1.9's Done-when checked `classList.contains("hidden")`, field values and `state` after every step, and passed completely while the editor was rendering behind the picker. Class toggles prove a thing is *shown*, never that it is *reachable*. **`document.elementFromPoint(x, y)` is the cheap check** — it answers "what would the mouse actually hit" — and a screenshot answers it for a human in one glance. Any session that opens one overlay from another owes itself one of the two.
- **`#canvas-body` is the app's scroll owner and it is shared by all six hubs.** `#main-canvas` is `height: 100vh; display: flex; flex-direction: column; overflow: hidden`; `#canvas-header` is its fixed child and `#canvas-body` is the `flex-grow: 1; overflow-y: auto; padding: 24px` one. **A hub that wants to scroll internally must NOT take `#canvas-body`'s overflow away** — that changes Dashboard, Prospect Hub, Media Hub, Campaign Hub and Data Management in the same edit. Make the view panel fill it and own its own overflow instead, so `#canvas-body` has nothing left to scroll while that hub is active. And express "screen minus header" as `height: 100%`, never `calc(100vh - <header height>)`: the flex column already solved it, and a hard-coded header height is a second copy that goes stale the first time the header wraps. Same rule as the sidebar note above — never recompute an offset the layout has already done.
- **`min-height: 0` is needed at every level of a flex chain, not just the scrolling element.** A flex child defaults to `min-height: auto`, which refuses to shrink below its content, so a single missing `min-height: 0` anywhere between the fixed-height ancestor and the scroll container makes the whole panel grow instead of the inner list scrolling. The symptom points at the wrong place — a sticky header that "doesn't stick," or a scrollbar that never appears — so check the whole chain before suspecting the scroll container itself.
- **A `<td>` must not be `display:flex`.** It stops being a table cell, so the row's borders and column alignment break under it while the contents look fine. Put the flex on a `<div>` inside the cell. Caught in the orphan window's Resolve column, 2026-08-29.
- **A header select-all checkbox is the exception to the rule below, and only that one.** Its handler *should* re-render the table, because it changes every row and the element it is bound to is rebuilt with the header rather than sitting under the cursor. The rule stands for anything per-row. TaskHub carries a comment at both sites saying the asymmetry is deliberate; do not "unify" them. Session 1.6.
- **A checkbox handler must not re-render its own table.** TaskHub's row checkboxes originally called `renderTaskHubTable()` on change; three consecutive clicks registered as one, because the first render replaced the tbody and detached the rows the later clicks landed on. It also drops focus and resets scroll. The pattern that works: mutate the Set, then repaint only the dependent text — `renderTaskHubSummary()` reads a module-scope `taskLastPageInfo` cached by the last real render, so it can run alone. Same trap applies to any per-row control whose handler currently calls a full render.
- **`.form-group input` styles EVERY input, which turns a radio button into a padded rectangle.** The rule sets `padding: 10px 14px`, a background and a border on `input`, `select` and `textarea` alike. It was written when every field in the app was a text box or a select; the bulk due-date modal (Session 1.7) added the app's first radio buttons and they rendered as boxes with a dot lost inside. **Fix it with a modal-scoped override** (`appearance: auto`, no padding/border/background, a fixed `width`/`height`, `flex: 0 0 auto`) rather than loosening the global rule, which every existing form depends on. Same trap waits for the first checkbox placed inside a `.form-group`.
- **`#modal-media-settings` is the app's single global settings home, and its id is a fossil.** It is titled "⚙️ Application Settings", is grouped by hub with a colored `settings-group-heading` per hub, and is opened by `openSettingsModal()` from a `⚙️ Settings` button in each hub's header (`btn-prospects-settings`, `btn-media-settings`, `btn-campaigns-settings`, and `btn-tasks-settings` from Session 1.7). **A new global setting belongs here, not inline in a view header** — that is where a person looks for it. Every section before Session 1.7 was an item list plus an inline add; the TaskHub date-mode `<select>` is the first **scalar** section, and it is populated at the end of `renderSettingsLists()` rather than by `buildRow()`. Do not rename the modal id to match the title without checking all six call sites.
- **An agent can exercise real listeners without the mouse** by calling `.click()` on the element the render function actually produced (`[...mem.querySelectorAll("button")].find(b => b.textContent === "+ New Task").click()`). This is strictly better than calling the handler directly for this codebase, because the failure mode being guarded against — `innerHTML +=` silently detaching a listener — is invisible to a direct call and fatal to a dispatched click.
- **A result row must commit on `mousedown`, not `click`, when the query field has focus.** A `click` on a search result fires after the field's `blur`, so any handler that hides or clears results on blur has already destroyed the row by the time the click lands, and the selection silently does nothing. `#task-prospect-results` rows use `mousedown` with `preventDefault()`, which also keeps focus in the query field so the keyboard path stays live. Session 1.9. The same applies to any future type-ahead in this app.
- **`Escape` inside a field that has its own clear behavior must `stopPropagation()`.** Otherwise the key does the field's job *and* whatever the surrounding modal does with Escape, and the user sees a modal close when they meant to clear a query. Session 1.9, `#task-prospect-search`.
- **In `style.css`, a new rule can lose to an old one at EQUAL specificity on source order alone, and the symptom never points at CSS.** The TaskHub blocks sit around line 160; `.table-scroll-container` and `.premium-table` are declared ~950 lines further down. Session 1.10 lost two rules to this in one sitting. (1) `#taskhub-thead th { position: sticky }` was beaten by `#taskhub-table th { position: relative }` written four rules later in the same new block — both `(1,0,1)` — and the header simply scrolled away while `classList`, the computed background and the opaque-alpha check all still passed. (2) `.taskhub-table-wrap { padding-top: 0 }` was beaten by `.table-scroll-container { padding: 12px }` — both `(0,1,0)` — leaving the header apparently mis-stuck. **Before adding a rule near the top of this file, grep for the class or element further down**; prefix with the view id (`#view-tasks .foo`) when the base rule is a bare class you cannot reorder.
- **A `position: sticky; top: 0` table header does NOT cover the scroll container's `padding-top`.** Sticky pins to the scrollport's padding edge, so any top padding is a strip the scrolling rows stay *visible* in — a sliver of the row above floating over an otherwise perfect opaque header. `.table-scroll-container` has `padding: 12px`, so every sticky-header table built on it needs `padding-top: 0`. Found by screenshot, 2026-08-30: every computed-style probe said "opaque and stuck" and every one of them was correct. **This is the 1.9 lesson again in a third form — a passing state check is not evidence the user can see the right thing.**
- **`table-layout: fixed` is required for per-column pixel widths to stick, and it changes what a too-narrow column does: it truncates instead of growing.** Session 1.5's `Due Date` default of 104px was fine under auto layout and rendered `"DUE DAT…"` under fixed, because the sorted column also carries a `▲`. **Every column needs a real default width once a table goes fixed**, and the sort arrow counts toward the widest label. Pair it with a width-less **trailing spacer `<th>` plus a `<td>` per row**, which soaks up whatever the real columns leave over — otherwise shrinking one column stretches its neighbours. Same trick as `makeTableColumnsResizable()` on the email-accounts table; TaskHub keeps `width: 100%` where that one uses `width: auto`.
- **Suppress a drag's trailing click with a one-shot module flag, not `stopPropagation()`.** A `mousedown` handler cannot see the `click` that follows it, and calling `stopPropagation()` on the mousedown does not prevent one. TaskHub's C16 handler sets `taskSuppressNextHeaderClick` on mouseup when the gesture was a resize or passed the 4px threshold, and the header's sort listener consumes the flag on its next call. Verified one-shot: the click after a drag does nothing, the one after that sorts normally. **Reach for this shape whenever a drag shares an element with a click** — the alternative, a drag implementation that swallows the click permanently, kills sorting silently.
- **A mouseup handler must not re-render the element the gesture happened on — the trailing click has not been dispatched yet.** The browser fires `click` after the `mouseup` handler returns. Rebuild the `<th>` inside that handler and the click arrives with no live target, so it never reaches the sort listener that consumes `taskSuppressNextHeaderClick` — and the flag, still standing, swallows the user's **next** genuine header click instead. The symptom therefore appears one gesture later than the cause, and every state check taken right after the drag passes. Session 1.11's drop handler deliberately does **not** call `renderTaskHubTable()`: the live shift has already moved the real cells, so the DOM is exactly what a re-render would rebuild. **Whenever a drag shares an element with a click, leave that element alone on mouseup** — and if a render is genuinely required, defer it past the click rather than calling it inline.
- **Pair a one-shot suppression flag with a clear at the start of the NEXT gesture.** A click always precedes the next mousedown, so a flag still set when a new `mousedown` arrives never reached its consumer at all — the click landed on the header row, or on nothing. Clearing it there is what keeps a leak to "one dead click" instead of "every header click dead from now on". Two lines, and it makes the flag's failure mode bounded rather than permanent.
- **Reorder columns by moving the real cells, not by painting a preview.** One function moves the header `<th>` and every row's `<td>` for a column together (`taskHubSwapAdjacentColumnCells`), which makes "cells drifted out of sync with headers" — correct data under wrong labels, the worst bug available in a table of other people's contact details — structurally impossible rather than carefully avoided. Moving a node also preserves its listeners, so a `th`'s sort handler survives being dragged across the table. Body rows are selected as `tr[data-task-id]` so the single-cell empty-state row is skipped.
- **Swap on the neighbour's MIDPOINT, in a `while` loop.** Using the neighbour's whole box oscillates whenever the dragged column is narrower than the one it displaces: the swap puts the pointer back inside the neighbour, which immediately swaps it back. With the midpoint rule the pointer always finishes on the far side of the boundary it just crossed. The loop is what lets a fast drag cross two columns between mousemove frames.
- **A drag indicator that must span a scrolling list belongs on `<body>` as `position: fixed`, not inside the table.** An absolutely positioned marker inside `#taskhub-table` would need a positioned ancestor, and `position: relative` on the table or its `th` is precisely what silently un-stuck the sticky header in Session 1.10.
- **Delegate a handler to a STATIC ancestor when the elements it targets are rebuilt every render.** TaskHub's header `<tr>` and `<th>`s are recreated by `renderTaskHubTable()`, so the C16 drag binds once to `#taskhub-thead` (static markup in `index.html`) and hit-tests `e.target.closest("th[data-col-key]")`. Binding per-`th` at render time would re-add the listener on every render. **`data-col-key` doubles as the opt-in**: the checkbox column and the trailing spacer do not carry it, so `closest()` returns null for them and they are excluded with no special case anywhere.
- **A hidden `<input type="hidden">` cannot be styled, focused, or read as a form control — and that is the point when replacing a `<select>`.** C14 changed `#task-prospect` from a select to a hidden input *keeping the same id*, so `saveTaskFromEditor()`'s `document.getElementById("task-prospect").value` never changed. **Freezing the id rather than the element is what made a UI replacement a zero-risk change to the save path.** Reach for this shape whenever a picker needs replacing: the id is the contract, the widget is not. Do not call `.options` / `.selectedIndex` on `#task-prospect` — it has none any more.

## Data, migrations and backup

- `wipeAllData()` must clear **both** `localStorage` and IndexedDB. Clearing one leaves orphans. **It also has to be edited by hand for every new top-level state array** — it clears an explicit list, not everything, and `state.tasks` was missed on the first pass in Session 1.3. A store left out of that list survives the wipe, which silently turns any export→wipe→restore drill into a test that cannot fail.
- **`convertToCSV()` quotes every field unconditionally and `parseCSV()` tracks quote state across newlines, so multi-paragraph values round-trip exactly** — verified in Session 1.3 against a note holding blank lines, commas and embedded `"` quotes, character-identical after export → wipe → restore. Do not add newline-stripping to protect the CSV; it does not need protecting. Note that **`parseCSVRow()` (a separate, simpler function ~8770) does NOT handle escaped `""`** — do not reach for it as an equivalent.
- **Restore functions trim their values (`cols[idx]?.trim()`); do not do that for a free-text body field.** Trimming is right for ids and enums and wrong for anything holding an email body, where leading and trailing whitespace is content. `restoreTasksFromCSV()` trims the header and BOM-strips it, and leaves the value alone.
- **`restoreSettingsFromCSV()` replaces each list wholesale whenever the CSV contains any row of that type**, so restoring an older backup drops values added since. The fix is not in the restore path: add the value to the first-run literal *and* push it idempotently in the `else` branch of `ensureStateDefaults()`, which always runs after a restore. Both halves are required (this is Phase 1 C6, and it is the general pattern for any new enum value).
- **A scalar setting rides in `prm_settings.csv` as a `["Name", value]` row** behind a `sawX` guard, following `Custom Sort Order`. That one row is what gives a settings object its DIRECTIVES §4 backup coverage — cheaper than a file of its own, and it restores through every path the settings CSV already reaches.
- New fields need a default in the existing state-defaults path (`ensureStateDefaults()` / `initializeDefaultState()`), or records predating the field read `undefined` and downstream code breaks on restore rather than on save — so the failure surfaces long after the change.
- `ensureStateDefaults()` always runs after a restore. That is the hook restore relies on for migrations.
- A feature that only mutates already-covered fields needs no new backup work. Check before assuming — the Advanced Query feature needed none. Session 1.6 was a second instance: it mutates `state.tasks[].status`/`.completedDate` and `p.history` only, both already exported and restored, so it added zero export or restore code.
- **`hist-${Date.now()}` collides inside any loop, and duplicate history ids are destructive, not cosmetic.** `recordInteraction()` mints one id per user action, so the idiom is safe there and unsafe the moment anything writes several entries in one pass — a bulk action completes three tasks in the same millisecond and gets three identical ids. `deleteInteraction()` filters on `h.id !== histId`, so deleting one entry would silently delete every twin, and the user sees two extra rows vanish with no error. Session 1.6 added `newHistoryId(prospect)` next to `logTaskCompletionHistory`, which appends `-1`, `-2` only on collision, following the `task-${Date.now()}-${i}` restore precedent. **Use it for any new history writer**; the same trap applies to `pros-`/`aud-`/`task-` ids in any bulk-create path.
- **A reachout is contact with a human — email, DM, phone call — and nothing else belongs in the reachout math.** Scope §8 originally counted task completion as a reachout; Michael reversed it on 2026-08-29 (scope §14), hours after Session 1.6 shipped it. The failure it was reversing is the same invisible class §8 feared, pointed backwards: counting internal prep work ("Research Jane's company") walks a prospect's last-contact date forward without anyone having spoken to her, and every filter downstream keeps returning confident, wrong answers. **The pattern for any future non-contact history type is `NON_REACHOUT_TYPES`, not "don't write the entry"** — the entry earns its place on the timeline; it just must not count. Keep the type registered in `state.reachoutTypes` (removing one changes what CSV restore does) and exclude it in the reachout math instead.
- **The single-writer rule survives its first "interesting" case, and that is the test it had to pass.** §14.4's transposition — a completion that really *was* contact logging an `Email` rather than a `"Task Completed"` — is one `reachoutType` parameter threaded `saveTaskFromEditor()` → `completeTask()` → `logTaskCompletionHistory()`, defaulting to `null`. It is deliberately **not** a second writer, because "this case is different" is exactly the reasoning that produces one. Session 1.9. Any future history variant follows the same shape: a parameter on the existing writer, never a sibling function.
- **A JSON payload survives the settings CSV intact — verified for real, not by inference.** Session 1.10's C17 row is `["Column Layouts", JSON.stringify(state.columnLayouts)]`, whose value is full of `"` characters; `convertToCSV()` writes it as `"{""taskhub"":{""order"":[""dueDate"",…]}}"` and `parseCSV()` reads it back. A full **export → `wipeAllData()` → restore through a real ZIP** returned the object **character-identical**. So a structured setting does not need a file of its own; one settings row is enough, and it inherits every restore path the settings CSV already reaches. **Wrap the `JSON.parse` in a try/catch that leaves the `sawX` flag DOWN** — one corrupt cell must not take every tag and reachout type in the same file down with it.
- **`state.columnLayouts` is the app's one persisted-UI-layout record, and future layout state joins it rather than starting a sibling.** Keyed by table id (`taskhub` is the only key in Phase 1), so a second table adopts it without a second implementation. Panel sizes and pane splits go in here under their own key: two stores means two migrations, two backup rows and two chances to miss one in `wipeAllData()`. Rename the field to `state.uiLayouts` if `columnLayouts` ever reads wrong — that is a rename with a defaults migration, not a new store.
- **The read-side migration rule is what makes a layout record safe, and it belongs in ONE resolver.** `taskHubColumns()` drops keys the build does not know and appends known columns the saved order never mentioned; `taskHubColumnWidth()` treats `0`/absent as "use the code default". That is what lets a later session add a column without breaking a saved layout, and what makes restoring an older backup — or one written by a newer version — safe. **Verified against a hand-edited record** carrying `"assignee"` and missing `"lastName"`: rendered clean, no errors, and `state` was left as saved (unknown keys are ignored on read, never deleted — deleting them would destroy a newer version's data on a round trip through an older build).
- **Exactly one function may write a given history entry type, and every path must route through it.** Scope §8's failure mode is the reason: a completion path that skips history does not throw, does not warn, and does not look wrong — `getLastReachoutDate()` simply under-reports, and the Advanced Query date filters keep returning results that are quietly incorrect. Session 1.6 therefore has `saveTaskFromEditor()` delegate its whole open→completed transition to `completeTask()` rather than setting `status`/`completedDate` itself, so there is no second place where a future edit could land the fields without the entry. **If a later session adds a third completion surface, route it through `completeTask()`; do not re-derive the field assignments.**

## Dates

- Store `YYYY-MM-DD` strings, not ISO timestamps. Timestamps inherit the off-by-one-day timezone bug class that already bit the Onyva weather date filter. Date-only strings compare cleanly as text, including for before/after/on filters.
- **`new Date().toISOString().split("T")[0]` is the file's oldest date idiom and it is UTC, not local.** It appears ~20 times in `app.js`. In America/New_York it produces *tomorrow's* date for anything created after 8pm — exactly the off-by-one class above, hiding inside the convention that was supposed to prevent it. **Task dates use `todayLocalDateStr()` instead** (defined next to `getCompanyName()`, Session 1.4). Use it for any new date field; leave the existing call sites alone unless a session is already touching them, since changing them is a data-meaning change, not a refactor.

- **Day-stepping arithmetic must run in UTC, not local time.** `shiftTaskDate()` (Session 1.7, contract C11) advances a `Date` one day at a time. A local-time `d.setDate(d.getDate() + 1)` across a spring-forward boundary lands on the *same* calendar day it started, because that local day is 23 hours — so a "+5 business days" shift silently arrives four days out, twice a year, in a way no test run in July will ever show. `Date.UTC(y, m, d)` days are always 24 hours. **Parse `YYYY-MM-DD` into UTC fields, step with `setUTCDate()`, read back with `getUTCFullYear/Month/Date`, and never let a local offset touch the value.** This is the same off-by-one-day class as the `toISOString()` note above, arriving from the other direction: there the bug is *reading* a local moment as UTC, here it is *doing arithmetic* in local time.

## Traps carried into Phase 2

Full reasoning in `DECISIONS.md`; these are here because this file is read every session and that one is not.

- **The blob shortcut.** Storing whole state as one hosted document caps at the 1 MB document limit and lets two devices overwrite each other wholesale — a silent total overwrite, not a merge conflict. Rejected on Gate B. If a future session proposes it as a quick win, read `DECISIONS.md` before agreeing.
- **The origin trap.** Today's data lives on the `localhost:5000` origin. A hosted app is a different origin with a different `localStorage` and **opens empty**. Prospects do not follow. The ZIP/CSV backup is the bridge, and Phase 2 needs an explicit import-and-verify step. Doing real work in a hosted copy before that produces two divergent databases.
- **The `saveState()` risk.** Granular writes sound like touching every mutation site across 10,000 lines. They are not: keep a shadow copy of last-saved state, diff on save, write only what changed. One function, no call sites touched. This converts the riskiest session in the build into an ordinary one.
- **The Gmail scope cliff.** `gmail.send` is a sensitive scope and cheap. *Reading* mail is restricted and buys a recurring annual third-party security assessment. "Detect the reply and auto-advance the sequence" sounds small and is not.

## Local snapshot backup (Phase 1 deliverable)

- File System Access API: `showDirectoryPicker()` once, persist the handle, write without re-prompting. Chrome and Edge only — not Safari, not Firefox. Vantage runs in Chrome app mode, so this is fine today and is a real constraint if the app is ever opened elsewhere.
- **The permission occasionally needs re-granting.** A snapshotter that fails silently is worse than no snapshotter, because it manufactures false confidence. A denied or failed write must surface visibly, not log and continue.
- Gate C means the session that builds this restores *from* a snapshot as part of its Done-when. Writing one successfully is not evidence.

### Findings from building it (Session 1.1, 2026-08-29)

- **A `beforeunload` snapshot leaves a real, correctly-named, ZERO-BYTE file when the page dies mid-write.** `createWritable()` creates the file immediately; if the page tears down before `write`/`close`, the file persists at 0 bytes and the read-back check never runs to catch it. The next boot then listed it as the newest snapshot, stamped `lastConfirmedAt` from its mtime, and showed **green while the newest snapshot on disk was empty** — precisely the lie C13 exists to prevent. **Fix: `listSnapshotFiles()` skips zero-byte files**, applying the writer's non-zero-size standard on the read side too. Do not remove that check. `beforeunload` additionally now only writes when there is an unprotected mutation, so reloads stop manufacturing corpses.
- **Anything called from `evaluateSnapshotHealth()` runs on every single `saveState()`.** The Data Management status panel listed the snapshots directory (a `getFile()` per entry) and it was landing behind every mutation in the app. It is now gated on `state.activeView === "data-management"`. The sidebar chip is the always-on surface and must stay cheap — it reads only the in-memory health object.
- **The permission model is per browser profile, not per app.** The File System Access directory handle lives in IndexedDB on the origin *in that profile*. A second Chrome profile (or the installed PWA if it runs under a different profile) opens with **no** backup folder and goes red. A session that verifies snapshots in one profile has proven nothing about another.
- **`showDirectoryPicker()` cannot be driven by an agent** — it opens a native OS dialog. Any session whose Done-when touches the backup folder needs Michael to click once. Clicking the health chip is the shortest path: with no folder set it opens the picker, and with one set it forces a snapshot.
- **Console read-back caveat for agent-driven verification:** Claude in Chrome's `read_console_messages` returns the whole tab history and stamps every message with the *read* time, not the emit time. Ordering within a read is therefore not evidence of ordering in the app. Clear the buffer, reload, then read, or you will chase phantom failures that are just replayed history.
- **The service worker needs two navigations to pick up a change**, not one: the first installs the new `CACHE_NAME` and leaves it waiting, the second activates it. A single reload after bumping the cache serves the *old* `app.js` and looks exactly like the fix not working.

### Findings from retention and the mirror (Session 1.2, 2026-08-29)

- **`prompt()` blocks the harness exactly like `alert()` does**, and `wipeAllData()` / `resetSandbox()` / `makeNewSandbox()` all gate on one. Stub `window.prompt` alongside `window.alert` for any agent-driven drill that touches them, and restore both in a `finally`.
- **An agent can run the full export → wipe → restore drill without a file dialog** by temporarily replacing `window.saveBackupFile` with a capture function, calling the real `exportZIPBackup()`, and feeding the captured blob back through the real `processRestoreFile()` as a `new File([blob], name)`. Only the final write-to-disk step is stubbed; the ZIP assembly, the router and every restore function are the real ones. This is how Session 1.3's Done-when was run.
- **`alert()` blocks the Claude-in-Chrome automation harness.** The restore path alerts twice (`applyJSONBackupText`, then the attachment count), and a blocked dialog stops the extension receiving any further command — the session looks hung, not failed. Any agent-driven restore drill must stub `window.alert` into an array, run the restore, and put the real one back in a `finally`. Do not "fix" this by removing the alerts; they are the right behavior for a human.
- **Snapshot time comes from the FILENAME, never from mtime.** Every file in a backup folder restored from cloud sync, copied to a new machine, or seeded by a test arrives with mtime set to the copy time. Reading mtime then reports a ten-week-old snapshot as written just now — precisely the C13 lie. `parseSnapshotName()` is the authority and `listSnapshotFiles()` carries the parsed value as `at`. This is also why a seeding drill's health-chip readings are meaningless: the chip is honest about *when the snapshot was taken*, and seeded files claim old dates.
- **Retention day/week buckets are the most recent buckets that CONTAIN snapshots, not calendar windows.** Read as "the last 14 calendar days," two weeks away from the app leaves rules 2 and 3 matching nothing, and the first run back prunes to the rolling 10 — deleting history exactly when it is least replaceable.
- **`planSnapshotRetention(files)` is deliberately pure** — an array in, a Map of name → surviving rules out, no directory handle anywhere. That is what makes ten years of fabricated dates testable in node in a second. The 30-file drill was *predicted* from it and then matched against the real pruner; keep that separation if the rules are ever amended.
- **Zero-byte corpses are now self-cleaning.** A reload can still leave one (see the 1.1 finding above); expect at most one boot warning, after which the pruner sweeps it. A *recurring* warning across many boots now means the pruner is not running, which is a real signal rather than known noise.
- **The mirror never deletes**, even when the attachment is deleted in the app — an older snapshot may still reference the blob. It also never re-writes an id it already holds, so a forced re-run is free and the mtimes on `snapshots/files/` do not move. Both are load-bearing: a mirror that forgets in step with the live database is not a recovery mirror.
- **Two browser profiles pointed at ONE backup folder is a trap, and it fires twice.** The handle is per profile (1.1 finding above), but the *folder* can be the same one — and then: (1) health lies. `initSnapshotSystem()` stamps `lastConfirmedAt` from the newest file in the directory with no notion of which database wrote it, so a profile whose own writer is dead boots **green** off another profile's snapshots. (2) Retention cannibalizes. A busy profile's snapshots fill the rolling-10 and the day buckets, pruning the quieter profile's history away. Neither the watchdog nor the pruner can tell two databases apart, because nothing in a snapshot identifies its origin. **Give each profile its own backup folder** unless and until snapshots carry a database id. Identified 2026-08-29 while handing off 1.2 — the sandbox profile was green and correct, and would have gone on looking correct after production was pointed at the same folder.
- The pruner touches `snapshots/files/` three guards deep — entry kind, name pattern, and an explicit name check. Any refactor of the directory walk must keep all three; deleting that directory silently strips every attachment from every snapshot that references one.
